# Authoring Quality Criteria

Use these criteria when creating or changing instructions, including this skill.
They are local authoring policy, not claims that every harness implements the
same tools or that upstream recommendations are mandatory requirements.

## Authority and change scope

- Explicit user decisions and applicable repository rules precede optimization
  defaults. Preserve concrete test gates, nondefault conventions and safety
  boundaries. Model-specific findings do not silently override team policy.
- Reuse approved plans and exact patches. Do not ask for the same approval per
  file. Ask only when a material choice remains or the action exceeds existing
  scope, is destructive, or an applicable rule explicitly requires new approval.
  State the exact reason and rule when approval is genuinely needed.
- Resolve selected targets and required dependencies before writing. A missing
  companion is a scope decision, not permission to create it. Already approved
  dependencies need no repeated confirmation.
- Keep source fetching read-only outside an explicitly selected cache-maintenance
  task. Report upstream drift; do not edit sibling/global caches, settings,
  catalogs or dates as incidental work. Register only user-scope skills when
  registration is part of the task; never register project-local skills globally.
- Within an active managed implementation, authoring supports implement-plan's
  selected items. It does not create competing plans, execution flags or archives.

## Capability and source contracts

Document capabilities first and host-specific names as examples. Use the active
host's file, patch, fetch, question and fresh-context delegation equivalents.
Only load deferred tools when the host supplies them. Try a source's equivalent
official HTML page when a Markdown MIME response is unsupported. If all fetch
paths fail, identify the cached source and date without pretending it was fresh.

A missing question tool does not imply headless operation: use normal text if
interactive. In headless operation, keep writes depending on a material unanswered
choice pending. Use supported model aliases or inherit the session. Missing
advisor/delegation is an explicit limitation, never an invented independent pass.

Label each guidance claim as upstream requirement, upstream recommendation,
local policy, or model/study-specific finding. Preserve source scope and exceptions;
do not turn a per-file size recommendation into an official combined hard limit.
Audit reference prose as well as file existence after renaming sections or roles.

## Evidence and completion

Keep these evidence levels separate:

| Level | Proves | Does not prove |
| --- | --- | --- |
| Structure/schema | Metadata, paths, parsing, size | Correct skill decisions or file changes |
| Decision replay | Interpretation of fixed inputs in a fresh context | Real tool execution, delivered question, completed pipeline |
| Artifact application | Actual output bytes, write order and preservation | Untested host integrations or branches |
| Live integration | Actual exercised host/tool flow | Other hosts, versions or unexercised cases |

Keep exact baseline inputs, fixture bytes, injected results and observed outputs.
Rerun those same cases on the candidate. If an existing explicit user instruction
already makes a baseline pass, report removal of an internal conflict rather than
inventing a FAIL→PASS improvement. A reproduced instruction contradiction supports
its targeted correction; speculative new behavior requires additional evidence.

Mock echo/keyword scores are parser or probe smoke results, never behavioral
success. Do not compare raw scores after changing the suite or executor. Inspect
supported grader schemas before adding fields; absent integration support may
use disclosed fresh-context/artifact checks when those satisfy the scoped task.

Give an evidence verifier originals/diffs, scope, facts, user decisions and the
effective guidance. A blind reviewer checks only properties observable from its
inputs; missing team approval evidence is not grounds for policy deletion.
Record PASS, FAIL, SKIP or UNVERIFIED per applicable check. Missing required
evidence blocks the relevant completion claim. Recheck changed criteria after
final repairs; do not restart all checks without a new reason.

## Maintenance termination

When repository policy requires skill-improver after edits, run it once for the
changed targets as a batch. Its bounded re-verification covers fixes within that
run, including self-maintenance; do not recursively invoke either controller.
The maintenance skill owns its successful-run timestamp. A targeted check is
not consent to a periodic full sweep, commit or unrelated cleanup.
